## SINGLE-BRAIN ARCHITECTURE INVARIANT

`server/src/services/scholarBrain.ts` is the ONLY AI brain, powering every workspace (OT-01, OT-07, OT-10, OT-15, OT-22). Only it may import `server/utils/llm.ts`; routes and services import `callOpenRouterJSON` / `callOpenRouterText` / `streamOpenRouterJSON` / `routedCompletion` from `scholarBrain.ts` (logged wrappers, not bare re-exports). No route or server module takes `routedCompletion` / `routedText` from `routerBridge` (guardian test; its keyring, availability and decorator exports are plumbing and fine to import). No file under `server/routes/` holds prompt text: prompts live in `server/src/services/prompts/` (`courseworkPrompts`, `journalPrompts`, `thesisPrompts`, `proposalPrompts`, `presentationPrompts`), reached as `scholarBrain.<workspace>Prompts` (guardian test). No workspace may add its own prompt engine, regex outline generator or subject-to-theory lookup table. New AI capability = new method on `scholarBrain`. Always follow `.claude/agents/single-brain-guardian.md` and `.claude/skills/single-brain-guardian/SKILL.md`.

**Permanently banned** (enforced by `src/__tests__/singleBrainGuardian.test.ts`, which fails `npm test`): the Quantum literature catalog (`quantumComputingCatalog` / `QUANTUM_COMPUTING_CATALOG`), the Zappos/Schein canned content (any `Zappos` string anywhere in `src/**`, `server/**` or `server.ts`; brief sanitizer, scope classifier and slide generator included), keyword-to-framework tables (e.g. "Bilateral Economic Interdependence Model"), and any direct `utils/llm` import outside `scholarBrain.ts`. Target frameworks come only from AI output or the student's own edits.

## Coursework (OT-01) pipeline

Four phases plus submission; everything is derived from the student's brief, never from a subject template. There are no literature catalogs, subject outlines or keyword-to-theory tables (banned by `singleBrainGuardian.test.ts`); the offline inquiry plan is `planBriefInquiries` (`src/domain/assignment/briefInquiryPlan.ts`). All Coursework prompt text (system roles, task prompts, the copilot personas) lives in `server/src/services/prompts/courseworkPrompts.ts`, reached only through `scholarBrain.courseworkPrompts`; the assignment routes, `src/domain/assignment` and `src/desk/assignment` hold no prompt text (guardian test); domain modules keep only types and answer parsers. Live routes validate bodies with zod (`server/routes/project/assignment/schemas.ts`), and no route answers with canned text when the AI does not. Server routes that wait on the AI save only the answer keys they changed (`saveChangedAnswers` in `assignment/helpers.ts` → `projectStore.patchAnswers`, an atomic JSONB merge via the `patch_project_answers` SQL function), never the whole record they loaded, so what the student saved meanwhile is kept; their AI calls take `abortOnClose(req)` so a closed connection stops the model. Every OT-01 save is mirrored into normalized per-stage tables (`assignment_projects`, `assignment_files`, `assignment_outline_sections`, `assignment_draft_revisions`, `assignment_submission_checks`, plus every source into `project_sources`; `server/src/assignmentRelational.ts` via `onProjectSaved`). Saved answers hold one key per setting (`src/domain/assignment/answerKeys.ts`; normalized by the project store on every save and load, so read and write only the canonical names: `assignment_brief`, `word_limit`, `academic_level`, `citation_style`, `title`, ...), and the client sends only changed keys. A source is approved only if its id is in the student's approved list (`src/domain/assignment/approvedSources.ts`: `isSourceApproved` / `selectApprovedSources` are the only check, UI included); `status: "kept"` is not approval, and no search or agent step approves anything. Word targets are clamped by `src/domain/assignment/wordLimit.ts` and the default citation style is `DEFAULT_CITATION_STYLE` (`answerKeys.ts`); write only canonical keys.
1. **Phase 01 Extract** (`AssignmentExtractStage.tsx`, `extractRoutes.ts`, `buildRoutes.ts`): paste or upload (`.pdf/.docx/.txt/.md`; the `File` goes straight to the handler and the input is reset; `/parse-brief` only reads the file, no AI call). **Save & Build** saves the brief and settings, then runs the one server build, `POST /assignment/build` (`useBriefBuild`): Extract (`extractStep`), then Understand (`understandStep`: the plan, then the outline with thesis options), three AI calls in one request, progress as SSE `{ step, status, message }` events, each result saved as it is ready, state in `assignment_build` (`{ state, step, hash }`). The workspace opens Understand as soon as the brief has been read. An unchanged brief and settings (same hash) do not run again unless `force`; one build per project at a time (409 `build_running`). `/agent/extract` and `/agent/understand` call the same step functions. Word count ignores course codes (`stripCourseCodes`: `QNT-4020` is never `4020`).
2. **Phase 02 Understand** (`AssignmentUnderstandStage.tsx`): brief-derived summary (`buildBriefSummary`), sub-question rows with the brief's own marks and proportional word targets (`parseBriefQuestions` + `allocateWordsByMarks`), grading criteria (`parseMarkingCriteria`), thesis selector. Parsers live in `src/utils/briefQuestions.ts` and start from `normalizeBriefLayout` (PDF text: a marks bracket split over lines, or title + marks + prompt on one line, is rejoined/split so both layouts parse the same). Sub-parts sit inside their question: totals, percentages and word budgets count main questions only (a stem's marks cover its parts). The rubric is read from its own heading (grade bands and question rows are skipped). The working thesis comes from the AI: the outline proposes up to three (`structure.thesisOptions`, shown as labelled "AI suggestion" cards; the first fills an empty thesis, never over the student's own), and "Refine with AI" (`POST /assignment/thesis/refine`) suggests a sharper version the student accepts or ignores (nothing saved until accepted). `briefGroundedStances` (`src/domain/assignment/briefThesis.ts`, the brief's own wording) are shown only when there are no AI options, labelled as not written by AI, and never fill the thesis on their own. Titles use `deriveDocumentTitle` (banner and inline metadata stripped). Until the student approves sources, only prescribed-in-brief sources count as approved.
3. **Phase 03 Sources** (`AssignmentSourcesStage.tsx`, `sourceRoutes.ts`, `agentRoutes.ts` (`/agent/sources`)): the search runs on the server, `POST /assignment/sources/search` (`{ queries?, topic?, limit?, includePrescribed? }`; the browser's `realScholarlyDiscoveryService.ts` only calls it, never a provider): up to 4 phrases (the student's, else the AI plan's `searchQueries` plus `buildSourceSearchQueries`, never the raw prompt), each through `retrieveSources` (scholarly). Records are merged into one per work (`dedupeWorks`, `src/shared/retrieval/identity.ts`), mapped by `src/domain/assignment/sourceSearch.ts` (stable ids per work; verification from `verifyAndConvertToCSL`: `verified` = citable with a DOI, `unverified` = citable without, `metadata_incomplete` = shown apart under "Needs checking", `splitNeedsChecking`; nothing filled in); relevance is the measured 0-100 `scoreSourceRelevance` over title, venue and abstract, never rescaled. References named in the brief are listed first with a `Prescribed in Brief` badge (`prescribedFromBrief`; a printed reference list is parsed into full entries with `parsePrescribedBibliography`, a named citation is looked up through the shared providers). Every query carries the brief's subject word and papers without it are dropped (`briefDomainTerms`). The AI's reading (`/agent/sources`) sees the thesis and each section's purpose, returns relevance, a `fit` line (shown as the reason), evidence quoted from the abstract and the sections a source supports; the list ranks by the AI's reading first (high, medium, unread, low), then measured relevance; drafting gives a section its mapped sources, else the approved sources mapped nowhere. Reference entries (APA 7, Harvard, IEEE, Chicago, Vancouver, MLA 9) come from the shared `citation_compliance` formatters (`formatters/bibParts.ts`; MHRA and already-truncated "et al." author lists stay local); author names go through `parsePersonName` (never "al., A. e.", never inverted). The Knowledge Vault is the third channel (`VaultSourcePicker`, `vaultSources.ts`; decrypted in the browser, items linked to the project). Every search result goes through `mergeSearchResults` (`services/sourceMerge.ts`): a re-run search replaces only unreviewed results (approved, bookmarked, prescribed, Vault, hand-added and removed sources stay), the same work is skipped by the shared identity rules (`sourceIdentityKeys`: DOI, arXiv id, title, short title + first author + year), and nothing found is approved for the student.
4. **Phase 04 Drafting** (`AssignmentDraftingStage.tsx`, `draftingRoutes.ts`): one section per main question of the brief (stem and sub-parts together; `groupBriefQuestions`), and no question is ever dropped (`ensureEveryQuestionHasSection`, also applied to AI outlines). **The AI decides the outline**: its headings, levels (H1 sections, H2 and optional H3 units: `level`, `parentTitle`), each section's `purpose`, `dependsOn`, `questionRef` and word budgets (`structureFromAi`, `src/domain/assignment/aiAssignmentOutline.ts`). Code only validates (`fitAiOutline`, `aiOutlineFit.ts`): the AI's budgets are kept in proportion and fitted to the exact total in clean multiples of 5 (10 from 1,000 words); a marked question the AI left uncovered gets a section titled from the brief (headings are never renamed); everything changed or noticed (scaling, an added question, a section whose share of the words is more than 20% from its question's share of the marks) is listed in `budgetNotes`, shown under the outline. The brief's questions and marks go to the AI as guidance (`briefQuestionsForOutline`). One section can be rewritten on its own (`POST /assignment/outline/section`, `replaceSectionFromAi`: same budget, written text kept). `applyMarksBudget` / `alignOutlineToQuestions` apply only to the plain starter outline (`generateDynamicAssignmentStructure`). `/stream-section` takes `allocatedWords` (capped by `remainingEssayWords`), asks for ±5%, counts words as the app does (`countProseWords`), streams the model's own tokens as they arrive (`callOpenRouterText` with `{ onToken, onReset, signal }`; a router fallback that drops partial output sends a `replace` event), and when short streams one visible continuation (a continuation that repeats the draft is dropped); Stop aborts the request and the server aborts the model; the text that had arrived is kept in `assignment_section_partials` (saved every 5 s while streaming) for Resume (`continueFrom`, from the last full sentence), Keep or Discard; one section is drafted at a time; long drafts are trimmed at a sentence boundary after citation tokens are expanded; each section gets a contract (`server/src/utils/sectionContract.ts`): every lettered sub-part, the citations the question names, its place in the report and the chosen writing style (`server/src/utils/sectionBudget.ts`). Refinement actions show only once a section has text. Submission shows the whole paper before it is downloaded (`FullDraftReview`, Phase 05): the written sections in order with the reference list, a Read/Edit switch (the shared `SectionTextEditor`, saving through the same `updateSectionContent` Drafting uses) and a full-screen view; the status facts sit on one line and the per-check cards are folded into "Checks in detail". The editor and submission show counted facts (paragraphs, citations matched to a source, unlinked paragraphs, checks passed), never a quality score, predicted grade, match-rate percentage or fixed analysis ratio; the intro/conclusion checks apply only to briefs that do not set their own questions. No outline is ever made up in place of the AI's: with none saved, `readStructure` returns an empty structure (`emptyAssignmentStructure` / `hasOutline`), Understand shows "No outline yet" with "Write the outline with AI" and "Start from a plain outline (not AI)" (introduction, one section per concept the brief names, conclusion; `briefOutlineSpecs.ts`; saved as `source: "starter"`), and Drafting asks for the outline first. A saved outline of old template text is removed, not replaced (`healCorruptedProjectStructure`). The Understand footer button approves the outline ("Approve outline & continue to Sources", sets `isConfirmed`). If every AI provider is out of credit, `/stream-section` sends a clearly labelled offline scaffold (`server/src/utils/sectionScaffold.ts`, built only from the section prompt, key points and approved sources) instead of dropping the request; failed revisions never overwrite existing text. The scaffold is shown beside the section with Try again / Insert, never saved as the section's text or counted as drafted words. The SSE stream opens (headers flushed, `: keep-alive` every 5 s; `server/src/utils/sectionStream.ts`) before the model call, after the 426 hand-off check (`handOffBeforeStream`); later failures are `{ error, recoverable: true }` events. When the cloud models fail and the next model in the chain is the student's own (a 426 can no longer be sent), the prompt of the first call goes back as a `{ requireFrontendLLM, challengeToken, systemPrompt, userPrompt }` event: the browser runs it on that model, streaming into the page, and re-sends the request with `llmResult` + `challengeToken`, which the server verifies against exactly that prompt and uses in place of a model call. Only sources with a title, an author and a year are offered for citation (never "Author" / "Scholarly Resource" stand-ins); the browser shows citation tokens formatted as they stream (`draftPreview.ts`). Paragraphs survive end to end: the prompt asks for 2-4 blank-line paragraphs, streamed tokens keep whitespace, and `src/shared/proseParagraphs.ts` regroups a single long block. No `[Unverified Claim]` tag is ever written into prose; unmatched citations are removed. The section editor is the shared TipTap `src/desk/editor/SectionTextEditor.tsx` (also used by Journal, and by Thesis chapters with `keepHeadingLevels`; round-trips the stored light Markdown). Coursework turns on `richBlocks`: underline (`<u>…</u>`), block quotes (`> `), pipe tables and paragraph alignment (`<p align="center|right|justify">…</p>` around a paragraph or sub-heading; left is never written), which every renderer reads through `src/shared/proseBlocks.ts` (preview, .docx tables, PDF `table` blocks, print view) and `countProseWords` counts without markup. The PDF is rendered on the server by the shared export pipeline (`POST .../assignment/export-pdf`, `src/desk/assignment/services/assignmentDocument.ts`); the print view is only a fallback. Exports (`exportText.ts`) never print the raw prompt, list only cited + prescribed sources (deduplicated) and render real italics. Saved projects are cleaned of legacy template text on load (`src/domain/assignment/legacyPurge.ts`). The approved sources are compiled into a `ReferencesCard` (alphabetical in the project style, copy/edit) and appended to the compiled draft. Per-question word counts the student types in Phase 02 are kept exactly (`applyQuestionWordTargets`); sub-parts get their own short titles and a single-prompt question never gets a child heading that repeats its title.

Viewing a stage writes nothing: `saveAnswers` skips unchanged values, `assignment_current_phase` is saved only when the student moves further than before, and a saved brief fills Extract's settings on screen without saving them.

## Retrieval, Ask Scholar and hand-off

- **One identity rule for sources.** `src/shared/retrieval/identity.ts` (`workKeys`, `isSameWork`, `dedupeWorks`) decides when two records are the same work, for `retrieveSources`, Coursework's merge, its exports and the agent's source step.
- **One retrieval path.** `src/shared/retrieval/providers.ts` is the only code that calls OpenAlex, Crossref, Semantic Scholar, Europe PMC and ERIC (also DOAJ, DataCite, arXiv, DOI and venue lookups; `webSearchEngine.ts`, vault and reference routes, `blueprintScout` all delegate to it). `server/src/retrieval/retrievalService.ts` (`retrieveSources`) is the one search entry: `/api/search/live`, Deep Research, Coursework's `/assignment/sources/search`, `scholarBrain`'s live evidence and the research pipeline (through `discoverScholarlySources` in `discovery.ts`), and the Journal Evidence Matrix (through `/api/search/live`). The browser searches no index itself; it only looks up records by DOI (Vault metadata and retractions, citation-graph snowballing), which stays client-side because Vault contents are encrypted there; the client `liveSearchService.ts` only calls that route and verifies the records (no browser-side provider fallback). Low-credibility domains live in `src/shared/retrieval/credibility.ts`. Providers never write filler snippets: no abstract means an empty snippet.
- **Ask routing** (search / chat / deep research) is one policy, `src/shared/askRouting.ts`, used by the server and the browser: the default is to ground the answer; only greetings, rewriting the user's own text, code and arithmetic skip search. When the rules cannot tell (`askNeedsSearchPlan`: auto mode, no attachments, not time-sensitive), the model decides: `POST /api/ai/ask/plan` → `scholarBrain.askSearchPlan` (one short JSON call, prompt in `src/shared/askPrompts.ts`) returns `{ search, query }`, the query being standalone so follow-ups search well. No answer (no AI, 426 hand-off, slow, bad reply) means the rules decide; the plan is never required.
- **One Ask path, with memory.** Every Ask answer goes through `POST /api/ai/agent` (the browser sends `streamTokens: true`: the words stream as SSE `token` events from the first token, the finished, citation-checked answer is the last `complete` event; a failure before the first token is plain JSON); the browser calls the model itself only on a 426 hand-off or when the server cannot answer (announced), never after the server reached the AI and it refused (`AskAiUnavailableError`: the same key would be refused again). Conversation memory is `src/shared/askConversation.ts` on both sides: last 4 turns nearly whole, older ones (up to 8) shortened, reference lists stripped from earlier answers. The route logs each prompt's size (`[ask] ... ~Ntok`).
- **Ask prompts** belong to `scholarBrain.askSystemPrompt` (`src/shared/askPrompts.ts`, shared with the browser fallback). Answers are written in the conversational voice (`voice: "conversational"`, `buildConversationalVoiceSystemPrompt`), the answer first, no form-like section labels, and only figures the sources give (`ANSWER_SHAPE`); the scholarly voice is for drafted prose. The system prompt is the same on every request (cacheable); the platform fact sheet is added to the user prompt only for questions about Scholar Core (`platformFactsFor`), and the answer rules are not repeated in the user prompt. **Quick budget** (`src/shared/askBudget.ts`): at most 8 sources, 600-character excerpts, a page fetched only for a source with no abstract. There are no canned platform answers and no code-writing refusal.
- **Ask composer and answer layout.** The answer mode is picked in one place, the Quick Scholar | Deep Research toggle (`ScholarFilterBar`), in the composer's one toolbar row beside the Year and Sources filter menus (on phones the row keeps attach, the toggle shown as Quick | Deep, an Options button and send; Year, Sources, citation style, settings and Vault open in its tray); the composer's **+** only attaches files (`PromptBarActionMenu`). Reference import lives in the Vault's Add Source dialog, not in Ask preferences. Under each answer: the answer, then one closed Sources panel (`src/desk/ask/SourcesPanel.tsx`: reference list and counts, sources found but not cited, excluded sources, the answer checks and "Open citation graph"), then the action bar and at most 3 follow-ups.
- **No invented data in Ask.** The citation graph uses OpenAlex metadata only: an unknown count, author, year or venue stays empty, never filled. There is no Evidence Matrix, meta-analysis, provenance inspector, consensus gauge, LaTeX export or timer-driven progress; `src/__tests__/askNoInventedData.test.ts` keeps them out.
- **Deep Research** plan: the card asks `POST /api/ai/deep-research/plan` for the model's own sub-questions (`formulateResearchPlan`, `fromModel`) and labels where they came from (`planSource`: AI, starter not written by AI, or the researcher's edits); a researcher's edits are never overwritten. Stage 4 is a real model cross-check (`analyseEvidence`); when it cannot run the stage is reported `skipped`, never as completed. The report call gets at most 40 sources (`selectReportSources`: Vault, scholarly/official, primary first; 600-character excerpts), and the citations returned are that same list.
- **Threads** persist in Supabase `ask_threads` (`server/src/askThreads/threadStore.ts`; migration `20261113120000_ask_threads.sql`, apply with the Supabase CLI). Documents attached in a conversation are kept with the thread and re-sent on follow-ups.
- **Hand-off** to OT-01/10/15/22 is `buildWorkspaceHandoff` (`src/domain/handoff/workspaceHandoff.ts`): conversation, documents, sources and style. Raw image bytes are not carried (the analysis stays in the conversation).

## What this is

A full-stack academic research/writing platform ("Scholar Core"): thesis, journal manuscript, proposal, assignment/coursework, presentation and peer-review workflows driven by AI agents, with a citation engine and a "Universal Vault" of sources. One Node process serves both the API and the React SPA.

Production: https://scholar.gkshah.com.np (Render, Docker, free plan).

- Path alias `@/*` → repo root (not `src/`).
- Server code imports shared modules from `src/` (citation formatters, document_intelligence, mesh agents) — keep those modules free of browser-only APIs.
- **Supabase**: Auth (GoTrue), Postgres with RLS, private storage buckets, Edge Functions (Resend email, search proxies). The server persists through Supabase's HTTPS Data API (`server/src/supabaseRest.ts`) using `VITE_SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`; `DATABASE_URL` direct Postgres is an optional fallback only.
- **AI**: AI Access has two tiers, Local and BYOK (Premium is "Coming soon" in the UI and has no code). One engine, `src/platform/router`; every workspace reads one central setting (keys + model per provider). 38 cloud providers (`src/config/providerCatalog.ts`) and every local runner (`localRunners.ts`) map onto the router (`providerMap`); keyrings hold up to 24 connections (`MAX_KEYRING_ENTRIES`), circuits open by failure kind per credential (`circuitBreaker.ts`, `server/src/ai/breaker.ts`), quick tasks try the `freeWorkhorse` providers first (`taskAffinity.ts`), and privacy settings (Local AI only, Confidential mode) filter the keyring (`privacyPolicy.ts`); details in `docs/AI-SYSTEM.md`; models are listed live from the provider (`/api/ai/models`), never named in code, and a provider with no chosen model uses the best one it lists ("auto"). The server also reads the signed-in user's saved keys (`accountAi`), so a new device works on its first request. App modules (`src/app/*`) take a `Completer` (`src/platform/completion.ts`): the server builds it in `server/src/ai/browserHandoff.ts`, the browser in `src/desk/ai/completer.ts`. Request bodies must never carry provider credentials (`rejectClientCredentials`); a user's own key reaches the server only as transient `x-ai-*` headers on AI routes (`routeUsesClientAi` in `src/desk/api/client.ts`).
- Deeper docs (kept in step with the code; update them in the same PR as the change): `docs/README.md` (index), `docs/ARCHITECTURE.md`, `docs/API.md`, `docs/DATA-MODEL.md`, `docs/WORKFLOWS.md`, `docs/AI-SYSTEM.md`, `docs/AI-CALL-MAP.md`, `docs/UI-UX.md`, `docs/DEVELOPMENT.md`, `docs/DEPLOYMENT.md`, `SYSTEM_MAP.md`, `SETUP.md`, `RUNBOOK.md`. Dated records (not current behaviour) live in `docs/records/` (`AUDIT.md`, `STATUS.md`, `PRODUCT_AUDIT.md`, `HOTFIX*_DEPLOY.md`, ...); `ROTATION_RUNBOOK.md` stays at the root.

## Slides & Keynotes (Presentation Studio, OT-22)

- Live route: `/presentation` (also mounted for OT-22 projects) → `src/desk/presentation/PresentationWorkspace.tsx` → steps `Step01Understand`, `Step02Design`, `Step03StudioCanvas` (aliased `Step03EditSlides`), `Step04Delivery` (aliased `Step04Present`) in `src/features/slides/components/`. `/presentation` works signed-out, which is handy for checking changes in a browser.
- Step 01 is a Gamma-style outline: upload or topic -> `POST /api/projects/:id/presentation/outline` (`scholarBrain.presentationOutline`; with no AI a brief-grounded outline from `src/shared/presentationBrief.ts`), editable cards (`OutlineBuilder.tsx`: title, visual type, bullets, reorder, add, delete, regenerate). Only a slide-count selector (6/8/10/12/15) remains. Titles come from `deriveDocumentTitle` (never an institution banner) and every extractor applies `cleanBriefText` / `stripCourseCodes`. Proceed builds slides via `generate-deck` with the outline (assertion-evidence copy) or `composeDeckFromOutline`. Step 02 adds `VisualPlanner.tsx` (the presenter picks Smart Diagram / Comparison Table / Multi-Card Grid / Custom Image per slide; nothing is drawn or numbered silently). Step 03 has the layout switcher (every layout), typed `+ Add Card / Block` menu (`gamma/blocks.ts`) and `Write with AI` (`POST .../presentation/write-block`).
- All slide rendering goes through `src/features/slides/gamma/`. Layout ids, copy budgets (`COPY_LIMITS`), the icon allowlist, `ThemeTokens` and the prompt's layout guide live in `src/domain/presentation/slideSchema.ts` (shared with `presentationCards.ts`); the model fills that schema and never writes CSS or coordinates.
  - `content.ts`: layout-independent `CardContent` + 15 layouts (incl. `grid3`, `grid4`, `pyramid`, `problem-solution`, `takeaways`). `getCardContent` derives content from legacy `blocks`; `writeCardContent` stores content and regenerates blocks (fingerprinted so copilot/Ask Scholar block edits still win).
  - `geometry.ts`: each layout → positioned primitives on a 1280×720 canvas. **Both** the web renderer (`GammaCard.tsx`) and `.pptx` export (`pptxExport.ts`, lazy-loaded pptxgenjs) draw these same boxes; change a layout here, not in a component. Overflow safeguard: a card that would leave the frame is re-laid out at 90/80/70 % type, then cut at the edge with `overflow: true` (editor hint). Icons are `kind: 'icon'` elements (`icons.ts`, also embedded as SVG in `.pptx`).
  - `theme.ts`: curated deck themes (hex tokens, no `#000000`; default `scholar-paper` #F8F7F4 / `scholar-ink` #171717), shape tokens (`radius`, `borderWidth`, `shadow`, `headingWeight`), `--slide-*` CSS variables, `ThemeTokens` converters + adapter for legacy library/custom themes.
  - `composer.ts`: offline deck builder; uses only figures present in the user's text. Server AI path: `server/routes/project/presentation.ts` + `presentationCards.ts` (zod-validated cards, ungrounded figures dropped).
- Never add invented metrics, citations or p-values to generators, fallbacks or demo content.

## UI conventions

- React 19 + TypeScript, Tailwind CSS v4 via `@tailwindcss/vite` (no tailwind.config; tokens live in `src/index.css` `@theme` / `:root`).
- Use semantic CSS tokens (`--bg-*`, `--surface-*`, `--text-*`, `--border-*`, `--accent*`, `--state-*`, `--theme-*`), not raw hex colors; lint rejects `#000000` and raw hex Tailwind classes (`bg-[#…]`) in app code (`src/desk`, `src/components`, `src/admin`, `src/features/coursework`, `src/features/understand`; deck themes carry colours as data). Dark mode = `data-theme="dark"` / `.dark` (custom variant). Changing a token must still pass `verify:contrast`.
- One sidebar (`components/navigation/ScholarSidebar.tsx`) serves the main screen and Presentation Studio. Headers that share width with a sidebar or drawer use container queries (`@container`), not viewport breakpoints. `document.title` is written only by `src/desk/documentTitle.tsx`. Never nest `<main>` or a button inside a button, and never give a control an `aria-label` that leaves out its visible text.
- Do not probe a local runner on page load (`services/localRunnerReachability.ts`: only when it is expected to succeed); a saved local connection is shown as "Connected" only after this browser has reached it.
- Icons: `lucide-react`; animation: CSS transitions/keyframes in `src/index.css` (no animation library); editor: TipTap.
- If you edit the inline theme script in `index.html`, update `INLINE_THEME_SCRIPT_CSP_HASH` in `server.ts` (lint will fail otherwise).
- Heavy libs are split via `manualChunks` in `vite.config.ts`; lazy-load large features.

## Deployment

- `main` is production. `.github/workflows/ci.yml` and `e2e.yml` run on every PR. `.github/workflows/deploy.yml` on push to `main`: `npm ci` → `npm run lint` → `npm audit --omit=dev --audit-level=high` → `npm test` → `npm run build`, then triggers the Render deploy hook (`RENDER_DEPLOY_KEY`), waits until `/api/health` reports the commit, runs `/api/health?deep=1` and the production smoke suite (if its secrets exist). `uptime.yml` checks `/api/health?deep=1` every 15 minutes.
- `render.yaml`: single Docker web service (`Dockerfile`, two-stage node:22-alpine), `plan: free` (cold starts, 512 MB RAM — keep `MAX_UPLOAD_MB` small), `autoDeploy: false` (deploys are triggered by `deploy.yml`), `healthCheckPath: /api/health`. Secrets are `sync: false` (set in the Render dashboard).
- `VITE_*` vars are baked in at build time (Docker build args). Anything secret must never be prefixed `VITE_`.
- Supabase migrations / Edge Functions are deployed separately (Supabase CLI), not by Render.

## Environment

Template: `.env.example` (all real `.env*` files are gitignored). Full inventory and what each variable does: `SETUP.md` §4. Keys the code reads: Supabase (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL`), crypto and security (`MASTER_KEY`, `LLM_CHALLENGE_SECRET`, `MAIN_ADMIN_EMAIL`, `VITE_CAPTCHA_SITE_KEY`, `CAPTCHA_SECRET_KEY`), AI and search (`TAVILY_API_KEY`, `SERPER_API_KEY`, `BRAVE_SEARCH_API_KEY`, `OPENALEX_API_KEY`, `ALLOW_SERVER_LOCAL_AI`), runtime (`PORT`, `NODE_ENV`, `MAX_UPLOAD_MB`). Email keys (`RESEND_*`, `ADMIN_EMAIL`) are Supabase Edge Function secrets.

## Rules

1. **Never** read out, log, modify, or commit `.env` files or secret values. When you need env info, list key names only.
2. **Never** push directly to `main`. Work on a branch; before pushing run `npm run lint` (must pass) and the relevant tests; run `npm run build` when touching build config, server entry, or imports shared between client and server.
3. Strict TypeScript: no `any` without justification, no `@ts-ignore` to silence real errors. Validate external input with zod.
4. Keep components small and modular; put pure logic in `src/domain` / services, not in components. Add or update tests next to the code (`__tests__/`).
5. Security-sensitive areas (auth middleware, RLS/migrations, userKeyVault, ssrfGuard, CSP, proxies) need extra care: preserve fail-closed behavior and add a test for the change.
6. New DB changes go in a new timestamped file under `supabase/migrations/`; never edit an applied migration. Check it with `scripts/db/replay-migrations.sh` against a local Postgres or `supabase start` (never production).
7. Dead code is not kept "for later": a module nothing reachable from `server.ts` or `src/main.tsx` imports, or an endpoint no client calls, is removed with its tests.
