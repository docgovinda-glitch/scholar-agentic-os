# Glossary — Canonical Vocabulary

> **Doc ID:** 02 · **Status:** Design · **Normative:** yes

Every capitalised subsystem name used anywhere in this documentation suite is
defined here. If a document uses a capitalised term absent from this glossary,
that is a documentation defect — file it.

Terms are grouped by kind. Within each group, alphabetical.

---

## 1. Named subsystems

These twelve names are the system's architectural vocabulary. Use them exactly.

| Name | One-line definition | Specified in |
|---|---|---|
| **Atlas** | The Output Type Catalog and its intake-schema engine: knows what a "Master's Thesis" is, what it requires, and what form to render | `14`, `30` |
| **Conductor** | The Workflow Coordinator. Owns gate state, schedules agent runs, enforces that nothing advances without human sign-off | `30`, `42` |
| **Console** | The web application. Quick tasks, review, approval, chat, sync status. Mobile-responsive. Deliberately not the Workbench | `23`, `24` |
| **Foundry** | The administrator's agent-authoring and evaluation environment. Where agent versions are written, evaluated against golden sets, and promoted to release channels | `49` |
| **Gateway** | The Model Gateway. Single abstraction over all AI providers: routing, failover, budgets, token accounting, per-task model binding | `41` |
| **Kernel** | The local runtime core running on the user's device: object store, index, event log, scheduler, capability enforcement | `40`, `44`, `45` |
| **Ledger** | The Provenance & Authorship Ledger. Records the origin of every span of text and every consequential decision | `32` |
| **Mesh** | The multi-agent runtime and the agent population within it | `42` |
| **Relay** | The optional cloud sync service. Stores ciphertext blobs and sync metadata; cannot read content | `44`, `48` |
| **Rubric** | The Submission Compliance engine. Compiles requirement sources into typed, continuously-evaluated rules | `31` |
| **Vault** | The Knowledge Vault. The user's optional long-term, encrypted, local knowledge corpus | `43` |
| **Warden** | The Privacy Guard. The mandatory egress checkpoint: classifies content, enforces per-provider policy, previews what would leave the device | `41`, `46` |
| **Workbench** | The desktop application. The primary workspace: multi-panel, dockable, offline-first, plugin-hosting | `22` |

### 1.1 Naming rules

- Subsystem names are **singular proper nouns**, never pluralised ("the Mesh",
  not "the Meshes").
- User-facing UI **MAY** use plainer language ("Knowledge Vault" rather than
  "Vault"; "Privacy Guard" rather than "Warden"). Internal documentation and code
  use the canonical name.
- New subsystems require an entry here before they may appear in another
  document.

## 2. Workflow and process terms

**Approved Corpus** — The set of sources a user has explicitly approved for a
Project. The only set that agents may cite from. Distinct from the Vault (the
user's long-term library) and from Candidates (discovered but unapproved).

**Candidate Source** — An externally discovered source awaiting the user's
decision in the Source Approval Queue. Has no citation identity and cannot be
referenced by any draft until approved.

**Claim** — An assertion in a draft that requires evidentiary support. Extracted
and tracked as a node in the Claim–Evidence Graph.

**Claim–Evidence Binding** — The typed link from a Claim to one or more Evidence
Spans in the Approved Corpus. A Claim with no binding is *unsupported*, which is
a compliance finding, not a silent condition.

**Evidence Span** — A specific, locatable region of an approved source (page,
paragraph, character offsets) that supports a Claim.

**Gate (G0–G7)** — A named checkpoint in the academic workflow. Each gate has
entry criteria, exit criteria, and a required human sign-off recorded in the
Ledger. Gates are: `G0 Intake`, `G1 Requirements`, `G2 Sources`, `G3 Structure`,
`G4 Draft`, `G5 Review`, `G6 Compliance`, `G7 Export`. Defined in `30`.

**Gate Sign-off** — The recorded human decision that advances a Project past a
gate. Carries actor, timestamp, and the state hash of what was approved.

**Intake** — The output-type-driven questionnaire that replaces the blank editor.
Generated by Atlas from the selected Output Type's intake schema.

**Output Type (OT-xx)** — A category of academic artefact (thesis, lab report,
grant proposal…) with its own structure, intake schema, quality gates, default
citation style, and workflow. Catalogued in `14`.

**Project** — The top-level unit of work. One Project produces one primary
Output. Owns its corpus, drafts, Rubric, Ledger, and gate state.

**Requirement Source** — An input from which compliance rules are derived: a
journal's author guidelines, a university handbook PDF, a department Word
template, a supervisor's email, or a user's manual entry.

**Session** — A continuous period of work in the Workbench. Sessions are the unit
for resource accounting and for the Resource Monitor.

**Workspace** — A container grouping related Projects, with shared settings,
Vault binding, and provider configuration. A user may have several (e.g.
"Doctorate", "Teaching", "Consulting").

## 3. Authorship and integrity terms

**Authorship Ratio** — The proportion of a document's final text, weighted by
span length, whose Ledger origin is human. Computed continuously, displayed in
the Workbench status bar, and included in the optional AI disclosure.

**AI Disclosure Statement** — An *optional*, user-editable declaration describing
how AI was used in a Project, generated from Ledger facts. Never mandatory,
never auto-attached without the user's action, never asserts work the user did
not perform.

**Laundering** — Rewriting AI-generated text to disguise its origin. Scholar OS
does not support this; the Ledger's origin attribution survives rewriting, and
`32` §6 specifies the refusal behaviour.

**Plagiarism Awareness** — Detection of unattributed overlap between the draft
and the Approved Corpus or the user's own Vault, surfaced as an actionable
finding with the source. Explicitly *not* a similarity score sold to
institutions.

**Provenance Origin** — The recorded source of a text span. The closed set is:
`human_typed`, `human_edited`, `ai_suggested_accepted`, `ai_generated_unreviewed`,
`ai_refined_accepted`, `quoted_source`, `imported_own_work`, `template`. Defined
authoritatively in `32` §3.

**Refinement** — Language improvement applied to human-authored text, recorded as
a tracked delta. Contrast with generation.

**Reviewed** — A span whose content a human has read in a context where review
was the explicit activity. Transitions `ai_generated_unreviewed` to a reviewed
origin. Scrolling past text does not constitute review; `32` §4.3 defines the
interaction that does.

**Unsupported Claim** — A Claim with no Claim–Evidence Binding. Blocks `G6` for
output types that require full evidentiary support.

## 4. AI and agent terms

**Agent (AG-xx)** — A bounded worker with a declared responsibility, typed input
and output contracts, a permission set, and an evaluation suite. Runs inside the
Mesh. Catalogued in `42`.

**Agent Channel** — A release track for agent versions: `dev`, `beta`, `stable`.
Users track a channel or pin a version. Managed in the Foundry.

**Agent Memory** — Per-agent retained state. Three tiers: `ephemeral` (single
run), `project` (scoped to one Project), `workspace` (across Projects, opt-in).
No agent has cross-user memory.

**Capability Token** — An unforgeable grant issued by the Kernel authorising a
specific capability (`read:draft`, `net:outbound`, `write:vault`…). Agents and
plugins hold tokens; the Kernel enforces them at the call boundary.

**Deterministic Mode** — Execution of an agent's task without a model call, using
rules or algorithms. Preferred where possible: cheaper, offline-capable,
reproducible. Many agents support both modes.

**Egress Class** — The sensitivity classification the Warden assigns to content
before it may leave the device: `public`, `bibliographic`, `derived`,
`user_content`, `restricted`. Policy is expressed per provider per class.

**Golden Set** — A fixed, versioned evaluation dataset with expected outputs, used
to test an agent version before promotion.

**Model Binding** — The mapping from a task to a specific provider and model,
resolved by the Gateway from user policy, availability, cost, and Egress Class.

**Provider** — An AI service or local runtime: OpenAI, Anthropic, Google, Ollama,
LM Studio, OpenRouter, DeepSeek, Qwen, Mistral, or a local GGUF runner.

**Run** — One execution of an agent. Has an ID, inputs, outputs, model binding,
token cost, duration, and a Ledger entry.

**Skill** — A reusable capability an agent invokes, below the agent level of
granularity (e.g. "summarise", "extract references"). Skills are composable and
individually testable.

**Tool Grant** — The set of tools (file read, web fetch, Vault query, draft write)
an agent version is permitted to invoke, declared in its manifest and enforced by
Capability Tokens.

## 5. Data and storage terms

**Artifact** — Any produced file: an export, a generated bibliography, a figure.
Distinct from the Draft, which is live state.

**Canonical Document Model (CDM)** — The internal, format-independent
representation of a document's structure and content. All parsing converts *into*
CDM; all export converts *out of* it.

**Canonical Reference** — The normalised, deduplicated internal representation of
a bibliographic source, independent of citation style. Formatters render it;
importers produce it.

**Content-Addressed Blob** — An immutable binary stored under the hash of its
content. How the Vault and corpus store PDFs, images, and media.

**Draft** — The live, editable text of a document section or the whole document.
Carries Ledger spans.

**Event Log** — The append-only local record of state transitions. The source of
truth for undo, sync, and audit.

**Index** — The local searchable representation of the corpus and Vault:
full-text plus vector embeddings. Rebuildable from blobs.

**Snapshot** — An immutable, restorable capture of Project state at a point in
time. The unit of version history and of local backup.

**Sync Envelope** — The encrypted unit the Relay stores: ciphertext, an
opaque object ID, and the minimal metadata sync requires. The Relay never sees
plaintext or document titles.

## 6. Compliance terms

**Compiled Rule** — A single machine-evaluable check derived from a Requirement
Source, with a type, a severity, a scope, and a message. The atomic unit of the
Rubric.

**Compliance Finding** — The result of evaluating a Compiled Rule against the
current draft: `pass`, `warn`, `fail`, or `not_applicable`, with a location.

**Requirement Extraction** — The agent-driven process of reading a Requirement
Source and proposing Compiled Rules. Always produces proposals for human review;
never silently binding.

**Rule Severity** — `blocking` (prevents `G6`), `required` (must be resolved or
explicitly waived), `advisory` (surfaced, not enforced).

**Rule Type** — The evaluation category: `structural`, `quantitative`,
`bibliographic`, `stylistic`, `formatting`, `metadata`, `ethical`.

**Waiver** — A recorded human decision to proceed despite a `required` finding,
with a reason. Appears in the compliance report.

## 7. Security terms

**Content Encryption Key (CEK)** — The symmetric key encrypting a specific object.
Wrapped by the Master Key.

**Key Custody** — The principle that the user holds the keys to their content. The
operator MUST NOT possess a key capable of decrypting user content.

**Master Key** — The root local key, derived from the user's passphrase and, where
available, sealed to platform hardware (Keychain, DPAPI, TPM).

**Recovery Kit** — The user-held material required to recover an encrypted Vault
or sync account: a recovery code plus, optionally, a printed key. The operator
cannot regenerate it. Loss is unrecoverable, and the UI must say so plainly.

**Sandbox** — The isolated execution environment for plugins: no ambient
filesystem or network, all I/O mediated by Capability Tokens.

**Trust Boundary** — A line across which data changes custodian: device↔provider,
device↔Relay, kernel↔plugin, user plane↔admin plane.

**Two-Plane Isolation** — The hard separation between the *user plane* (user
content, user keys, user agents) and the *admin plane* (operator tooling, admin
AI, analytics). Administrative AI has no path to user content. Specified in `49` §3.

## 8. Surface and UI terms

**Dock** — A region of the Workbench that accepts Panels: `left`, `right`,
`bottom`, `editor`. Panels move between docks.

**Layout Preset** — A saved arrangement of Panels. Ships with presets per workflow
phase (Discovery, Drafting, Review, Compliance).

**Panel** — A self-contained Workbench UI unit with an identity, a preferred dock,
and a state contract. Examples: Knowledge Explorer, Agent Monitor, Citation
Explorer.

**Quick Task** — A Console interaction completable in under two minutes on a
phone: approve sources, read a section, ask a question, check a run.

**Surface** — One of the three product frontends: Workbench (desktop), Console
(web), Mobile (responsive Console plus native shell affordances).

## 9. Terms deliberately not used

To keep the vocabulary honest, these words are banned from this documentation and
from user-facing copy, with the reason and the replacement.

| Banned | Why | Use instead |
|---|---|---|
| "AI-generated paper" | Describes a thing we refuse to build | "AI-assisted draft" |
| "Humanize" / "humanizer" | Industry term of art for detector evasion | "Language refinement" |
| "Undetectable" | Only meaningful in a cheating context | — (no replacement; the concept is out of scope) |
| "Autonomous writing" | Implies no human in the loop | "Agent-assisted drafting" |
| "Smart" (as a feature adjective) | Says nothing | Describe the actual behaviour |
| "Plagiarism score" | Invites institutional misuse | "Attribution finding" |
| "Hallucination" (user-facing) | Jargon that normalises the failure | "Unverified claim" / "unsupported claim" |
| "Just" / "simply" (in instructions) | Condescends to the exact users we serve | Remove |
