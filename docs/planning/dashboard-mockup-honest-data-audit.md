# Dashboard Mockup — Honest-Data Audit (2026-07-28)

**Purpose**: apply this project's standing fabrication discipline to the
new deep-navy mockup (see `docs/planning/sci-fi-redesign-scoping.md`'s v3
section for the visual-direction record) *before* any of it gets built.
Every panel below is classified as **(a) real** — backed by data the app
already has and can show truthfully today; **(b) buildable** — real, but
needs identified work first, and the *shape* of what's shown must change
from the mockup's literal numbers; or **(c) unbuildable** — cannot be made
honest at all with this app's real architecture, and should not carry
forward into implementation on the assumption it can be "filled in later."
Findings are grounded in the actual data model (`src/types.ts`,
`useProjectPersistence.ts`), not assumed from the mockup's own framing.

## Classification

| Panel (as shown in the mockup) | Class | Why | Real equivalent / action |
|---|---|---|---|
| **Onboarding stepper** (1 Workspace/Login, 2 AI Models/Configure, 3 Knowledge Vault/Connect, 4 Ready/Launch) | **(a) real** | Maps directly onto `OnboardingStep` (`login` → `ai-setup` → `knowledge-vault` → `workshop`), already the app's real state machine. | Keep as-is, wire to the real `onboardingStep` value — no design change needed. |
| **"SECURE CONNECTION — ENCRYPTED • PRIVATE" badge** | **(b) buildable, but not as a single unconditional claim** | Conflates two different real things: transport security (whether this page is actually served over HTTPS — a real, checkable fact this app currently does *not* verify anywhere) and key-storage encryption (the BYOK vault's real XOR/AES-adjacent local encryption, which *does* exist and *is* true). Showing "encrypted" unconditionally when the page could be served over plain HTTP would be a false security claim, not a design flourish. | Split into two independently-real, independently-checked claims: (1) gate any "secure connection" wording on `window.location.protocol === "https:"`, shown honestly as absent/different copy when false (e.g. local dev over HTTP); (2) a separate, always-true "Keys encrypted locally" claim backed by the real vault encryption already shipped. Never merge them into one badge that's true only some of the time. |
| **AI KERNEL — "ONLINE"** | **(b) buildable, must reflect real health-check state, not a static claim** | No standalone "AI Kernel" service exists to be online/offline — `AIKernel` (per `CLAUDE.md` §3) is real but internal, not a network service with a health endpoint. The closest real, user-facing signal is the currently-configured provider's live health check, already built (`AIGateway.healthCheckProvider`, used throughout `AIControlCenter.tsx`). | Rename to reflect what's actually checked (e.g. "AI Gateway" or "Active Provider"), and show the real, live result — including genuinely offline, not just "Online" as a fixed label. Same standard already applied everywhere else in this app (`AIControlCenter`'s "Current AI Mode" status card). |
| **ACTIVE MODELS** — 5 providers (Claude 3.5, GPT-4o, Gemini 1.5 Pro, Qwen 2.5 72B, Ollama) all shown "Online" simultaneously | **(c) unbuildable as shown; (b) buildable once reframed** | Explicitly flagged in this task. Showing 5 fixed providers, all green, regardless of what the user actually configured, is fabricated redundancy. | Show only the provider(s) genuinely present in the current `aiSettings`/`fallbackOrder`, each with its own real, live health-check result (including offline/checking states) — the same data `AIControlCenter`'s "Local Models" and "Providers" tabs already compute. A user with one configured provider sees one row, honestly. |
| **AI AGENTS — "12 Active"** | **(c) unbuildable as a live concurrency count; (b) buildable as a static or logged count** | The app has no background job queue or concurrent-agent execution model — agents (`src/agents/*`, 7 wired: literatureReview, researchPlanner, knowledgeGap, researchQuestion, methodologyAdvisor, statisticalAnalysis, integrityReviewer; `manuscriptWriterAgent` remains unwired per `HANDOVER.md`) run synchronously, on demand, per user action. There is no real sense in which N agents are simultaneously "active" at any given moment. | Either a static, honest "7 agent types available" (real, unchanging count of what's actually wired), or a real, timestamp-derived "Agent calls today: N" pulled from `usageLogs` entries filtered to the current date — never a live "active" count implying concurrency that doesn't exist. |
| **SYSTEM STATUS** — CPU/MEMORY/GPU/STORAGE percentages, "All systems operational" | **(c) unbuildable, remove entirely** | Explicitly flagged in this task. No browser API exposes real host CPU, GPU, or system-memory utilization to a web page — `performance.memory` (Chrome-only) reports the JS heap, not system RAM; there is no cross-browser CPU/GPU read API at all. "STORAGE: 2.4 TB" as shown implies device storage, which is equally unavailable and, even if it were, is not something this app manages. | Remove this panel's hardware-monitoring framing entirely — it cannot be made honest. If a "status" panel is still wanted here, replace it with genuinely available signals: the real AI-gateway online/offline state (see AI KERNEL above), whether the key vault is locked/unlocked, and — if a storage number is wanted at all — `navigator.storage.estimate()`'s real quota/usage for this origin, which is a real API but reports realistic browser-storage figures (KB-MB for this app's actual data), not terabytes, and must be labeled as browser storage, not device/system storage. |
| **Global counters** — PAPERS 12,842,761; JOURNALS 34,128; CITATIONS 88,671,221; DATASETS 6,731 | **(c) unbuildable as platform-wide aggregates; (b) buildable as per-scholar counts** | These read as a shared, multi-user corpus size. This app has no such backend — it's a local-first, single-scholar tool; there is no database aggregating papers/journals/citations across users, and building one is far outside this redesign's scope. | Reframe entirely as the *current scholar's own* real counts, at real (small) scale: "Papers" → `allProjects.length` (the scholar's own project count, realistically 1-few, not millions); "Datasets" → `project.dataSources?.length` (real, per-project, from the already-built `DiscoveredDataSource[]` field); "Journals"/"Citations" → see the dedicated rows below, since both need additional persistence work first. The numbers will be small and honest, not impressive — that's the correct outcome, not a shortfall. |
| **KNOWLEDGE VAULT — "4.2 TB"** (left constellation node) | **(c) unbuildable at this scale; (b) buildable at the real scale** | `KnowledgeVault.files` (`VaultFile[]`) stores uploaded documents with a real `fileSize` field, but realistically at KB-MB scale for a research tool's actual usage, not terabytes — browsers' storage ceilings (`localStorage`/IndexedDB) make TB-scale figures impossible for this app's real architecture regardless of how it's implemented. | Show the real, summed `fileSize` across `project.knowledgeVault.files`, in KB/MB (whatever the true value is) — never inflated to look impressive. |
| **LITERATURE REVIEWS — "128"** (left node) / **"4 Active reviews"** (right rail) | **(c) unbuildable as shown; (b) buildable, much smaller, reframed** | "128" reads as another global aggregate (see counters above) — same problem, same fix (per-scholar, not platform-wide). No persisted "reviews" list exists to count from today. | If wanted at all, reframe honestly at real scale and real meaning: e.g. a real count of the scholar's own projects currently sitting in the literature-review phase (0 or 1, almost always), not an "active reviews" figure implying concurrency this app doesn't have. ## Summary — what this means for implementation

Of the panels the mockup shows: **4 map directly to already-real data**
(onboarding stepper, research projects count, draft papers count, most of
the bottom nav); **8 are buildable but require either reframing the
number's scale/meaning or real persistence work that doesn't exist yet**
(secure-connection badge, AI kernel/gateway status, active models,
AI agents count, global counters reframed per-scholar, knowledge vault
size, today's research, journal suggestions, storage utilization); **5
should be removed outright** as unbuildable with this app's real
architecture (system status hardware panel, collaborators, running
agents, literature-reviews-as-shown, prompt studio and marketplace nav
entries). None of the (c) items should carry forward into implementation
on the assumption "we'll wire it up later" — per this task's own
instruction, they are marked for removal from the design now, not
deferred.
